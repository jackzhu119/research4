# 云主机重启后的续算与追加授权

本次用户原话为“进展如何，补上授权 10 万 cpu 时继续运行”。按本线程一贯的 CPU 秒口径记录新增 100000 CPU 秒，原 900000 CPU 秒与新增授权合计 1000000 CPU 秒。新增授权单独追加，不重置原 SQLite 账本、原协议或既有结果。独立的光谱机器学习预算不计入此处。

重新连接后，内核 boot_id 已从 `acde02b8-169c-4e86-829a-bea19b373c18` 变为 `97b25e20-3f81-4718-9ff9-bc5fd5692a2b`。重启前的 `running` 快照和 PID 不能证明当前仍有计算。原 43 个冻结文件的 SHA 校验全部通过，SQLite `integrity_check` 为 `ok`；变更前已使用 SQLite 在线备份保存账本及校验回执，位于 `recovery_records/20261112T234328Z/`。

两构象此前各有两次进程收到 SIGKILL（退出码 -9）。四次已有 wait4 终账的 CPU 总和为 41417.069162 秒；当时单进程 CPU 上限为约 43–45 万秒，因此不是达到该 CPU 上限。四次都在电子 SCF 收敛并通过独立 fresh-Fock 审计后进入核梯度阶段，尚未保存完整电子结构点。不能把它们算作四个成功实验，也不能把重复起点计算算成优化步。另两个旧 boot 下尚未终账的进程需单独恢复记账，将已观测 CPU 下界与无法核实部分的保守上界分别记录；不会把整个长租约直接宣称为实际 CPU 消耗。

对 PySCF 2.13 源码的静态检查表明，75 原子、grid 5 的原始 Becke 网格响应张量与二阶 AO 数组合计约 7.84 GiB/进程；生成器切换原子时还可能暂存旧数组。双梯度并发可超出当前主机的 16 GiB 限额。旧内核的内存事件不可获取，所以内存耗尽是有明确证据支持的风险解释，尚不能写成已由 OOM 日志证实的原因。

续算采用单个化学 worker，保留 PBE/def2-SVP、同一积分网格、RI-J 辅助基、网格响应、辅助基响应与全部原收敛和质量标准。资源 adapter 只提前释放公式中已不再需要的临时数组，不关闭响应或降低网格。使用前需验证原始网格权重、权重响应及小分子梯度等价。

每个构象的 `attempt-002/.local/rolling.chk` 有完整轨道和占据记录，其原子顺序、75 原子几何、762 个 AO、320 个电子、方法及文件 SHA 均需重新核对。恢复轨道后必须重新执行原 fresh-Fock、能量和电子数审计；通过后才接续核梯度。恢复记录及新资源代码的 SHA 单独保留，原科学源文件不改写。无法通过复核的检查点仅可作为显式记录的初始密度，不能被直接标作合格结果。

此时尚无通过核验的完整优化点、极小值或新振动/IR 谱。是否完成由实际原始数组和资格审计决定，不能由进程存在或 CPU 消耗推断。
